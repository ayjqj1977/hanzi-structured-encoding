# 汉字结构化编码三个多月全记录：从18维手工特征到"帮手变拖累"的消融实验

**写在前面**

我不是AI研究者，没有实验室，没有算力。我是一个快五十岁的中年人，干过送货、快递、保安、监控，一直在底层讨生活。九十年代末念了个计算机应用大专，出了学校就再也没碰过专业，二十多年干的活和代码毫无关系。用两三个月的业余时间、一台没有独显的轻薄本、和几百块钱的云训练费，一路从18维手工编码折腾到消融实验。实验还在失败，但失败的原因越来越清楚了。

这篇不是论文，不是成果汇报。是一个人在一条小路上走了两三个月，想把自己验证过的东西记下来——哪些方向走通了，哪些被消融实验证伪了。如果有人也在琢磨"汉字结构特征能不能帮上语言模型"，希望这里有的脚印能让他少踩几个坑。

---

## 一、起点：18维手工编码（2026年3月）

### 1.1 问题

主流中文NLP的做法是：汉字 → 随机初始化768维向量 → 海量语料训练 → 模型自己"发现"规律。

但汉字不是无结构符号。214个部首决定了字形大类，五笔编码把每个字拆成了结构单元，四角号码定位字形空间，拼音有明确的声韵调结构。这些人类整理了几千年的信息，在Embedding层被完全忽略。

当时已有的工作（部首增强词向量、五笔中文分词、四角号码改进表示）的共同模式是：每种结构特征单独做Embedding，再拼接。我的想法不同——把四角号码、五笔、拼音、声调压缩成一个18维固定数值向量，**不靠学习，纯规则映射**。

### 1.2 编码设计

| 维度 | 内容 | 取值 | 说明 |
|------|------|------|------|
| 1-5 | 四角号码 | 每维1-9 | 捕捉字形空间结构 |
| 6-9 | 五笔编码 | 每维1-26 | 4个字根键位 |
| 10-15 | 拼音编码 | 声韵母映射 | 捕捉语音结构 |
| 16 | 声调 | 1-5 | 四声+轻声 |
| 17-18 | 字符类型 | 分类标记 | 区分汉字/字母/数字 |

### 1.3 验证结果

用6000个常用汉字的18维编码计算余弦相似度，对比随机整数编码：

| 指标 | 18维结构化 | 随机编码 | 判别力倍数 |
|------|-----------|---------|-----------|
| 音近字相似度 | 0.9685 | 0.7119 | **1.55x** |
| 形近字相似度 | 0.7316 | 0.7163 | **1.17x** |
| 随机字相似度 | 0.6247 | 0.7173 | 更分散 |

### 1.4 18维的局限

- 18维 vs 768维，信息容量差40倍以上
- 形近判别1.17x偏弱：四角号码前3位相同的字可能字形差异巨大
- 五笔4字根等权计算：第1字根（通常就是部首）被稀释
- 字符类型维度在纯汉字场景下全为0，完全浪费

### 1.5 18维时期的三个关键预判

1. **五笔第1字根 ≈ 部首**：单独提取作为部首代理，可能是零成本形近信息源
2. **结构化先验作为初始化**：不是用18维替代768维，而是用结构信息约束初始化分布
3. **可学习编码器**：用MLP处理离散结构特征，提供先验同时允许模型调整

这三个预判后来全部进入了34维的架构设计。

## 二、知识图谱尝试：最早的弯路（2026年3月14-17日）

在18维编码验证完成后、34维设计开始之前，走了一段弯路：知识图谱。

2026年3月14日，用 `extract_knowledge_graph.py` 从 OneGraphV2 中文知识图谱中提取了大量三元组（实体-关系-实体），生成 `corpus_knowledge_graph.txt`（约270MB）。然后用 `merge_corpus.py` 将古文诗词、知识图谱文本、汉字/词语/成语/歇后语全部合并为 `corpus_combined.txt`（约285MB），放在 `云端完整训练_含知识图谱` 目录下训练。

想法很朴素：古诗文能给模型文言的韵律感，知识图谱能给模型结构化的事实知识，合在一起训练应该能"优势互补"。

但效果不好。三元组的语法模式太单一（基本都是"X-关系-Y"），模型很快过拟合到这种固定句式上，生成的内容变得机械。3月17日把整个目录打包成zip存档，放弃了这条路线。

回头看，这次尝试最大的教训是：**语言模型的训练语料需要自然语言的多样性**。结构化知识的注入方式需要更精巧的设计（如预训练后微调、或单独编码为知识嵌入），直接混入原始语料不是好方案。

不过这次尝试无意间促成了后续语料的"渐进剥离"思路——既然知识图谱不行，那就把它去掉；后来发现古文也不行，那就把古文也去掉；最后发现纯现代文最好，就只用现代文。每一次剥离都是消融实验的预演。

---

### 语料演进：三次剥离

从3月到6月，训练语料经历了三次逐层剥离：

| 阶段 | 时间 | 语料构成 | 代表版本 |
|------|------|---------|---------|
| 第一阶段 | 3月12-17日 | 古文诗词 + 知识图谱三元组 + 词典数据 | 18维 |
| 第二阶段 | 5月30日-6月7日 | 古文诗词 + 现代文（百科/新闻/科学/文化）混合 | V2-V5 |
| 第三次剥离 | 6月10-16日 | 纯现代文大规模语料（~418MB） | V6 |
| 第四阶段 | 6月18日起 | article级超大语料（~2GB） | V10-V12 |

第一层剥离是去掉知识图谱（3月17日），第二层剥离是去掉古文（6月初），第三层是全面转向article级现代文（6月18日）。

这个渐进剥离的过程本身就像消融实验：每去掉一层，观察模型行为变化。只是当时没有意识到，直到6月24日才用消融实验的方法论来设计对照实验。

## 三、进化：34维CNN编码器（V2-V6）



### 2.1 过渡：32维尝试（2026年5月27-28日）

在18维和34维之间，短暂尝试过32维编码。当时生成了大量32维向量CSV/XLSX文件（7743字×32维），试图在18维的基础上扩充更多字形特征。但32维的结构设计不够清晰——哪些特征值得加、如何分组、CNN通道如何切分——这些问题没有满意的答案。

最终决定推倒重来：不修修补补18维，而是直接设计一个全新的34维框架，用清晰的6个信息通道取代"什么都在一个向量里"的思路。两天的32维尝试虽然废弃了，但它促成了"分通道CNN"这个核心架构想法。

### 2.2 为什么要升级到34维

18维的问题是"把连续的笔画结构硬塞进离散的分类编号"。四角号码把整个字压缩成5位数字，信息损失太大。解决方案是让编码器直接在原始笔画数据上做卷积。

### 2.3 34维的设计

> **注**：34维并非“纯字形”编码。其中维度26-31是拼音声韵编码（语音信息），维度10-12是部首索引。它本质上是**字形+语音+部首**的多源结构化编码，而非单一的笔画几何描述。以下为实际维度结构（依据 vector_info.txt）：

34维分成6个信息通道：

| 维度 | 通道 | 类型 | 说明 |
|------|------|------|------|
| 0-4 | 四角号码的5位 | float | 从18维继承 |
| 5-8 | 五笔字根4位 | float | 从18维继承 |
| 9 | 总笔画数 | int | 新增：笔画结构特征 |
| 10-12 | 部首索引 | float | 新增：部首在214部首体系中的定位 |
| 13 | 部首外笔画数 | int | **关键新增**：18维预判的部首独立 |
| 14 | 同码组编号 | int | 新增：形近字分组 |
| 15 | 结构类型 | int | 新增：独体/左右/上下/包围 |
| 16-25 | 笔顺编码1-10 | float | 新增：笔画顺序编码 |
| 26-31 | 拼音声韵编码 | float | 新增：声韵母结构编码 |
| 32-33 | 符号索引 | int | 新增：字符级别标识 |

### 2.4 CNN架构

34维不是一次性喂给Transformer，而是经过一个**5路CNN编码器**分段处理：

```
四角号码 [0-4]  → Conv1d(k=2) → 64ch
五笔     [5-8]  → Conv1d(k=2) → 64ch  
笔统     [10-12] → Conv1d(k=2) → 64ch
坐标     [16-25] → Conv1d(k=3) → 64ch
方向     [26-31] → Conv1d(k=3) → 64ch

离散特征：笔画数、部首、同码组、结构、符号 → 各自Embedding
所有输出拼接 → 416维 → 融合层 → 516维 → 12层Transformer
```

- V2-V6 参数：**42.7M**
- 训练数据：V2-V5阶段使用古文+现代文混合语料（corpus_ancient + 百科/新闻/科学等现代文），V6起完全剥离古文，经过 corpus_combined_filtered → corpus_final → corpus_clean → corpus_modern 的多轮清洗，最终使用纯现代文语料约418MB
- V10起使用约2GB（约1.9GB）article级语料（corpus_v10_article.txt），为第四阶段语料
- 训练设备：AutoDL云端 A100（约100块）

### 2.5 V6的性能天花板

V6是纯34维架构的最终版本（V7未成功训练）。

**语言建模能力**：PPL = 59.56（测试值，训练记录 best_loss = 2.59，对应训练PPL约13.55）

差距的原因：训练时在训练集上按长序列计算；测试用100篇不同主题短文，seq_len=64小窗口估算。两者评估方式不同，但59.56这个量级说明了一件事：**纯34维可以出可读的文字，但语言建模能力远不如标准方案**。

**形近字判别**：18对形近字，17/18易区分（余弦 < 0.5），1对一般（辨-辩，余弦 0.66）。平均余弦相似度 0.1958。

这个结果有意思：34维做语言模型不行，但做字形编码器相当好。它在向量空间里把形近字推得很开。

**生成样例（V6纯34维）**：

> Prompt: 人工智能技术的快速发展正在深刻改变
> 生成: 人工智能技术的快速发展正在深刻改变了人类，循环神经网络和Transformer架构在自然语言处理方面取得了革命性的

前半句通顺，后半句跑偏——这是纯34维的典型表现：能做局部连贯，但缺乏长程语义一致性。

## 四、混合策略的引入：34 + 64（V8-V12）

### 3.1 从V8开始加可训练语义向量

V8首次加入 `semantic_dim = 64`——一个随机初始化的、可训练的 `nn.Embedding`，与冻死的34维CNN输出拼接：

```
34(冻死, CNN编码) + 64(可训练, 随机初始化)
↓
98维 → 融合层 → 768维 → 12层Transformer
```

- V8-V9：5路CNN架构，fusion_input=480（320CNN+96Emb+64语义），经Linear投影到d_fusion=512，max_seq_len=V8:384→V9:512
- V10：新架构 NeuroGlyph34V10，d_model=512，参数 **~43M**（50000步训练）
- V11：窗口切片策略（256字窗口，128步长），扩展到100000步
- V12：升级d_model=768, n_heads=12, d_ff=3072，参数 **~92M**
- 训练设备：AutoDL云端 vGPU-32GB

加入64维可训练向量后，效果大幅提升：

| 版本 | 语义向量 | PPL | 形近字判别 |
|------|---------|-----|-----------|
| V6（纯34，d_fusion=516） | 无 | 59.56 | 17/18 |
| V12（34+64） | 64维可训 | **10.07** | 17/18 |

PPL从59.56降到10.07，语言建模能力提升了近6倍。但形近字判别没有变化——64维学到的是语义信息，不是字形信息。

### 3.2 34维到底帮没帮上忙？

这是困扰我整个V10-V12阶段的问题。

34维冻死嵌入（实际是查表获取的34维字形特征，不再经过CNN实时编码）占了98维的34/98≈35%的维度位，但它不参与梯度更新。训练时只有64维在学。最坏的情况下，34维不仅没帮忙，还在**抢占维度预算**——Transformer看到的总维度是98，但其中只有64的梯度在流动。

一个残酷的类比：你给模型768维预算，但其中35%是"死肉"。如果把死肉换成活的，会怎样？

## 五、消融实验：帮手还是拖累？

### 4.1 实验设计

**对照组（V12）**：34维冻死CNN + 64维可训练随机向量 = 98维总输入

**实验组（消融）**：**96维纯随机可训练向量**（无34维CNN）

为保证公平：维度对齐（98 vs 96，接近），架构完全相同（NeuroGlyph34V10类），训练超参数完全一致（10万步，V10基线为50000步），同一台服务器。

### 4.2 训练过程

| 指标 | V12（34+64） | 消融（96随机） |
|------|------------|-------------|
| 最终 train_loss | 3.30 | **3.18** |
| 训练中 val_ppl | — | 14.16（波动下降） |

消融版训练loss更低，但val_ppl偏高——这是**过拟合更快的信号**。34维冻死层可能起到了正则化的作用。

### 4.3 本地测试结果

用相同的100篇短文测试集、相同的PPL计算方法、相同的18对形近字：

| 指标 | V12（34+64） | 消融（96随机） | 胜负 |
|------|------------|-------------|------|
| PPL | 10.07 | **9.66** | 消融胜 |
| 形近字判别 | 17/18 | **18/18** | 消融胜 |
| 生成质量 | 通顺但有跑偏 | **更通顺、主题更稳定** | 消融胜 |

**96维纯随机可训练嵌入在三个指标上全面优于34(冻死)+64(可训)**。

### 4.4 这意味着什么

冻死的34维不是帮手。它是**拖累**。

它占着维度位，不贡献梯度，降低有效参数利用率。去掉它，把相同的维度预算全部分配给可训练的随机向量，模型反而学得更好。

形近字判别尤其打脸：我花了几个月设计的34维手工特征，在形近字判别上（17/18）**不如**96维随机向量的训练结果（18/18）。这不是34维没有形近信息——V6证明它的字形+语音多源编码确实能区分形近字——但**冻死不让人家学**，效果还不如从零开始随机初始化后让模型自己发现。

### 4.5 但34维的正则化作用是真实存在的

训练过程中消融版的val_ppl波动更大、过拟合更快。34维冻死层虽然限制了性能上限，但可能提供了**输入空间的稳定锚定**，让64维的学习更稳健。去掉锚后，96维纯随机更自由地学，最终上限更高，但训练稳定性更低。

## 六、V6词表Bug事件：一个差点被误判的版本

测试V6时，PPL显示347,133——比随机猜测还差。排查后发现测试脚本 `test_v6.py` 硬编码了从V10目录加载 `char_to_idx.json`。

V6和V10虽然共享7987个字符，但**每个字符在词表中的索引完全不同**。测试时用V10词表编码文本 → 取出的是别的字的34维特征 → 模型收到垃圾输入 → PPL爆炸。

修复后发现：V6实际PPL=59.56，生成可读但不是347,133那种纯乱码。

**教训**：工具链中的索引映射是最容易出错也最难察觉的bug。不同版本的训练脚本维护独立的 `char_to_idx` 和 `embedding_matrix` 是潜在的地雷——每次版本间交叉测试都要确认映射一致性。

## 七、这段时间来的核心结论

### 6.1 34维CNN编码器的定位

它是一个**好的字形编码器**，但不是一个好的语言模型组件。

- 形近字判别17/18：在向量空间里把形近字推得很开
- 但冻死不训练，语言建模需要的是可训练参数

如果把它当作一个**字形相似度引擎**（计算字与字之间的形状距离），它可能有用。但如果把它焊死在语言模型的Embedding层冻死不训练，它会变成拖累。

### 6.2 可训练 > 手工设计，当维度预算固定时

这个结论不需要"34维是垃圾"来证明。核心洞见是：

> 在固定的维度预算下，可训练的随机向量比冻死的手工特征更有效。

34维的特征质量如何、是否包含字形结构 —— 这些问题不重要。重要的是**它在占据预算但不参与学习**。只要维度池里有一条鱼在吃空饷，把空饷换成劳动力，团队整体效率就提升。

### 6.3 如果还想用34维，可能的出路

1. **不冻死，让34维CNN也可训练**：但这可能让CNN权重被语义信号污染，失去纯字形编码的纯度
2. **单独训练一个字形编码器，离线导出向量**：训练完成后把CNN权重固定，输出34维向量作为预计算的字形特征库，然后像用word2vec一样查表
3. **缩小占比**：比如只用10维CNN特征，留更多预算给语义向量
4. **换个场景**：语言模型不是34维的终点，字形相似度引擎、OCR纠错、生僻字识别可能更合适

### 6.4 五笔第1字根的预判偏了

18维时期我说"五笔第1字根≈部首，单独提取可能是零成本形近信息源"。这个方向在34维里用部首Embedding（维度13）实现了，但消融实验证明：即使部首信息被CNN编码进了34维，冻死后对端到端训练的贡献为负。

不是部首信息没用——是冻死了一切都白搭。
