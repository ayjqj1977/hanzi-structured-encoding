# HZK32 1024点阵编码：让模型真正"看见"汉字

> 一个280K参数的编码器，用128字节的真实像素，在消融实验中全面压制frozen方案。但CNN 5-Stream以13.55 PPL提醒我们：可训练才是关键，位图不是唯一答案。

---

## 一、背景：为什么走到1024点阵

这件事的起点在《从18维到消融实验》那篇。当时我们做了一个汉字字形编码方案，分三步走：

1. **18维手工特征**：笔画数、部首、结构类型（上下/左右/包围）等，纯人工定义。能用，但上限很低。

2. **34维 CNN frozen**：用预训练的5路CNN从多种字体图片中提取字形特征，冻住不参与训练，作为额外的输入嵌入拼到语义embedding旁边。思路是"白嫖视觉信息"。

3. **消融实验揭示问题**：把34维frozen拿掉，PPL居然不降反升——说明这34维冻死的向量不但没帮上忙，反而在拖后腿。

结论就是一句话：**冻死的向量不如不用的向量**。

但这不是否定字形信息本身的价值。换个角度想：如果34维frozen是负贡献，那问题出在哪？两个可能性：要么字形信息本身没用，要么"frozen"这个策略有问题。直觉是后者——CNN在不同字体上预训练、然后压缩到34维、再冻死不给梯度，中间每一步都在丢信息。

**同期验证：CNN 5-Stream。** 在PointMatrix实验的同时，另一条线用同样的5路CNN架构但把所有embedding改为可训练——34维CNN字形特征 + 部首/结构/笔画数等5个额外特征 → 融合 → d_model=516，42.71M参数。在相同语料上训练到step 33480，PPL达到**13.55**。这验证了一个关键假设：CNN字形信息本身有价值，问题确实出在frozen策略上。

HZK32 1024点阵是另一条验证路径：用最原始最干净的位图数据，配一个极简的可训练编码器，让模型自己决定怎么用这些像素。

## 二、HZK32字库介绍

### 什么是HZK32

HZK32是中文DOS时代的标准宋体32×32点阵字库，GB2312编码，覆盖6768个汉字。每个汉字占128字节，按区位码依次排列。读取公式：

```
offset = ((区码 - 0xA1) × 94 + (位码 - 0xA1)) × 128
```

文件总大小约846KB。每字的128字节展开后是一个32×32=1024位的二值矩阵——只有0和1，没有灰度，没有抗锯齿。

## 三、架构设计

### 整体架构

```
Token ID → ┌─ semantic_embed (可学习) ──→ 64维 ─┐
           │                                       ├─ cat(128) → Linear → 512 → 12层Transformer → LM Head
           └─ glyph_matrix[buffer] → PointMatrixEncoder → 64维 ─┘
```

模型主干是12层Transformer（8头、d_ff=2048、max_seq_len=512），参数约42.3M。与标准Transformer的唯一区别在于输入层：每个token的表示由两路拼合而成。

### PointMatrixEncoder：极简可训练编码器

```python
class PointMatrixEncoder(nn.Module):
    def __init__(self):
        self.encoder = nn.Sequential(
            nn.Linear(1024, 256),   # 1024位原始点阵 → 256
            nn.LayerNorm(256),
            nn.GELU(),
            nn.Linear(256, 64),     # 256 → 64维字形编码
        )
```

设计要点：

- **输入**：1024维原始二值点阵（0/1），来自`register_buffer`——存储时冻结不占梯度，但作为编码器的输入，梯度通过编码器反向传播。
- **双层Linear + GELU**：没有用CNN、没有用Attention、没有任何花活。1024→256→64，就是两层全连接。
- **输出**：64维字形编码向量。
- **端到端可训练**：这是和V6 34维frozen方案的本质区别。编码器的权重随语言建模loss一起更新，模型自己学会哪些像素特征对预测下一个字有帮助。

- **参数量**：`1024×256 + 256 + 256×64 + 64 = 279,360`，仅占模型总参数（42.3M）的**0.66%**。

### 与语义embedding的融合方式

```
glyph_feat (64维) + semantic_embed (64维) = 128维 → Linear(128→512) → LayerNorm → GELU → Dropout
```

两路各占64维，平等拼接后通过一层Linear升到512维，再进入Transformer。没有门控、没有加权、没有复杂的融合机制——最简单的拼接+投影。

设计直觉是：编码器自己会学会在64维空间里分配"哪些位放字形信息、哪些位留给下游自由发挥"。强行设计精细的融合机制反而可能限制表示空间。

### 词表处理：7987 → 6622 → 6726

V6的原始词表有7987个token。但HZK32只覆盖GB2312汉字区的6768个字——标点、数字、英文字母、特殊符号都没有点阵数据。

处理分两步：
1. **裁掉无HZK32的字**：7997 → 6622，只保留在HZK32中有对应点阵的GB2312汉字。
2. **补回功能性字符**：6622 → 6726，补回103个标点/数字/字母，这些token的glyph向量全部置为零向量。

补回字符用零向量而非随机向量的理由：零向量进入编码器后输出恒定，语义embedding完全承担表示职责。如果用随机向量，编码器会尝试从中"读出"不存在的字形信息，反而引入噪声。

### 为什么64维就够了

这是一个直觉性的设计选择，背后有推理：

- 1024位原始点阵包含的是**真实的结构信息**，不是随机编号。笔画连续性、部首位置、间距比例都是物理世界中存在的规律。
- 编码器的工作是**压缩**而非**记忆**——从1024维有结构的空间中提取64维泛化特征，比记忆一个7987行的随机embedding table高效得多。
- 对比：V6的34维frozen向量，平均每对形近字的余弦相似度高达0.71（见第七节），说明34维不足以保留区分性信息。64维是一个经验上足够且不至于过参数化的折中。

## 四、训练过程

### 训练配置

| 项目 | 配置 |
|------|------|
| 平台 | AutoDL，RTX 3080 Ti（1.58元/时） |
| 语料 | `corpus_v10_article.txt`，715M字符，约1,393,794个训练样本 |
| 模型 | 42.3M参数 |
| Batch Size | 16×4=64（梯度累积） |
| Max Seq Len | 512 |
| 学习率 | 1e-4，warmup 2000步后余弦衰减 |
| 总步数 | 50,000（实际跑到45,000） |

### 踩过的坑

以下是训练过程中实际遇到的6个问题，每个都有故事：

#### 1. nohup日志不刷新

在AutoDL上用`nohup python train_pointnet.py &`启动训练，等了十分钟`train.log`还是空的。

原因：Python的stdout默认有缓冲区，`nohup`环境下只有缓冲区满了或程序退出才会刷盘。

修复：在脚本开头加一行 `sys.stdout.reconfigure(line_buffering=True)`，同时训练循环里所有`print`改走一个`prlog()`函数——双写stdout和`train.log`文件，每次写完后`flush()`。两重保险。

#### 2. 全量tokenize导致OOM（56GB）

第一版Dataset的逻辑很简单：`corpus_v10_article.txt`读进内存，逐字符`char_to_idx.get(ch, unk_id)`转成int列表，返回`list[int]`。

715M字符的文本，Python字符串本身占~715MB，转成list[int]后每个int占28字节（Python对象overhead），加上dict lookups的临时对象，内存直接飙到56GB——3080 Ti的机器只有16GB RAM + swap，当场OOM kill。

修复：不在`__init__`里全量tokenize，改为**按需tokenize**——`__getitem__`被调用时才从文件中seek到对应位置，只tokenize需要的`max_seq_len+1`个字符。内存降到可控范围。

#### 3. DataLoader逐字查dict太慢

按需tokenize解决OOM后，遇到了新问题：每个batch都要从文件读文本、逐字查dict。dict lookup在Python里虽快（平均O(1)），但每个epoch要做1.4M次lookup、每次遍历1.4M个字符——DataLoader成了瓶颈，GPU利用率只有30%。

修复：**预tokenize到`.ids.mmap`**。首次运行时将全文tokenize为`np.memmap(dtype=np.int32)`文件。memmap是OS级虚拟内存映射，`__getitem__`直接切片取`int32`数组，不用读文本、不用查dict、不用Python对象转换——存储从715MB降到5.5MB，`__getitem__`耗时从毫秒级降到微秒级。

#### 4. 梯度累积死循环

梯度累积的标准写法是 `if (step + 1) % grad_accum_steps == 0`。但代码里写的是：

```python
if (step + 1) % 4 == 0:   # 期望：每4个微批次更新一次
```

实际上`step`的更新放在了条件分支**里面**——只有当条件为True时`step`才自增。所以`step`永远是0，`(0+1)%4`永远不等于0，条件永远不触发。模型跑了"几千步"实际上一步都没更新。

修复：把梯度累积的计数器独立为`accum_step`，与全局`step`解耦。`accum_step`每微批次+1，到4清零并触发`optimizer.step()`和`step += 1`。

#### 5. loss显示0.001实际应该8.8

训练循环里的loss计算：

```python
loss = criterion(logits, y) / grad_accum_steps
total_loss_accum += loss.item()
```

`loss.item()`拿到的是**除以4之后的平均loss**。日志里打印`total_loss_accum / batch_count`，得到0.001，看起来模型已经收敛到完美，实际上：

```
真实loss = 0.001 × 4 × 512 = 2.048    (还远未收敛)
```

修复：日志统计改为累积`loss * grad_accum_steps * tokens`，再除以总token数：

```python
total_loss_accum += loss.item() * grad_accum_steps * y.numel()
# ...
avg_loss = total_loss_accum / tokens_accum
ppl = exp(avg_loss)
```

修完后真实的loss从"0.001"跳到了8.8，PPL约6600，符合刚初始化的预期。

#### 6. 日志频率从100步改到10步

初始设置每100步打一次日志。在AutoDL上训练时，100步约等于2-3分钟——两次日志之间的空白期太长，完全不知道模型是在正常跑还是卡死了。加上前面梯度累积死循环的教训，改为每10步打一次日志（约15秒一次），训练曲线一目了然。

## 八、为什么128字节的像素能打败384字节的随机向量

这是一个反直觉的结果，值得专门分析。

### 数据量对比

| | V10 34维frozen | PointMatrix 64维 |
|------|-------------|-------------------|
| 存储格式 | 34个float32 | 64个float32 |
| 字节数 | **136字节** | **256字节** |
| 信息源 | 5路CNN从多字体图片提取 → 压缩到34维 | HZK32原始位图 → 编码器压缩到64维 |
| 原始信息 | ~384字节随机向量（96个float32等价） | **128字节结构化位图** |

等等——输入端的对比更有意思：

| | V10字形输入 | PointMatrix字形输入 |
|------|----------|-------------------|
| 原始数据 | CNN中间层特征（多字体图片压缩） | HZK32 32×32二值位图 |
| 原始大小 | ~384字节（96 floats） | **128字节** |
| 数据结构 | 连续值特征向量 | **0/1位图，每个bit有明确的空间位置** |

PointMatrix用**更少的原始字节**（128 vs 384），提供了**更多的有效信息**。

### 为什么128字节的位图更"有效"

HZK32的128字节不是128个随机bit。它们携带的是：

- **笔画连续性**：一个横笔画的像素在矩阵中形成连续的水平线段，不是散点。
- **空间拓扑**：撇从左上到右下，捺从左下到右上——每个像素的位置编码了笔画的走向。
- **部首关系**：同一个部首在不同汉字中的像素模式是一致的。编码器学会"木字旁"的特征后，对所有含"木"的字都有效——这是天然的**组合泛化**。
- **间距比例**：上下结构 vs 左右结构 vs 包围结构，像素分布完全不同，编码器可以直接从空间分布中学习结构类型。

而V10的34维frozen向量，输入给模型的是96个浮点数——模型看到的是一串没有空间语义的数字，不知道第几个数字对应哪个位置的笔画。虽然这些数字是CNN从图片中提取的，但34维的压缩率太高（1024位 → 34×32位 ≈ 等量），压缩过程中丢弃了大量的空间结构信息。更致命的是frozen策略：编码器永远无法根据语言建模任务的需要调整这些数字的解读方式。

### 编码器的真正工作

PointMatrixEncoder不是死记硬背1024个像素的排列。它从训练中学会的是：

```
横画位置 → 特征A
竖画位置 → 特征B
撇捺角度 → 特征C
部首分布 → 特征D
结构类型（上下/左右/包围）→ 特征E
...
```

这些泛化特征构成了64维空间的基底。形近字在这个空间中天然接近（因为它们共享大部分结构），只需要微调少量维度就可以区分——这正是"未/末"余弦从0.725降至0.219的机制。

**核心理念：给模型真实的结构信息，哪怕字节更少，也比更多的随机噪声强。**

## 九、结论

### 实验总结

三条路线，相同语料（`corpus_v10_article.txt`），三种字形编码方案：

| 方案 | 架构 | PPL | 步数 | 参数 |
|------|------|-----|------|------|
| V10 (34-frozen) | 34维CNN frozen + 64 semantic | 18.37 | 50,000 | 42.3M |
| PointMatrix | HZK32 1024位图 → 64可训练 + 64 semantic | 14.20 | 45,000 | 42.3M |
| **CNN 5-Stream** | 5路CNN可训练 + 5额外特征 | **13.55** | 33,480 | 42.71M |

关键对比：

| 维度 | V10 (34-frozen) | PointMatrix (HZK32) | CNN 5-Stream |
|------|----------------|---------------------|--------------|
| PPL | 18.37 | 14.20 | **13.55** |
| 收敛速度 | 最慢 | 15K步超18.37 | 最快（推断<10K步） |
| 生成质量 | 不可读 | 5/5通顺 | 未测试 |
| 形近字判别(cos) | 0.713 (负优化) | **0.417** | 未测试 |
| 额外参数 | 0 | 279K | ~300K |
| 原始信息 | CNN压缩特征 | **128B位图** | CNN+手工特征 |

### 四点启示

1. **可训练 > 信息源。** CNN字形在frozen时是负优化（18.37），改为可训练后跃升到最优（13.55）。同样，V12 baseline（34 frozen + 64 semantic，d_model=768，92.2M参数）增大模型容量而未改frozen策略，预期仍受限于同一瓶颈。决定因素不是CNN vs 位图，而是梯度能否回流到字形编码器。

2. **PointMatrix证明了位图的信息效率。** 128字节的真实位图，仅用两层Linear就把PPL从18.37拉到14.20——距离CNN 5-Stream的13.55仅差4.6%。且形近字判别（cos=0.417）是所有方案中最优的。如果CNN 5-Stream也做形近字测试，结果会是一个有价值的对照实验。

3. **Frozen是系统性瓶颈。** V10的34维frozen让形近字cos从原始0.653恶化到0.713。V11（同架构，d_model=512，42.9M参数）和V12 baseline（d_model放大到768，92.2M参数）虽然模型容量递增，但如果34维字形仍是frozen，瓶颈不会消失。V12 ablation（0字形+96纯随机语义）是消融对照组，验证去掉字形信息后的退化程度。

4. **极简设计有独特优势。** PointMatrixEncoder就是两层Linear+GELU，279K参数。CNN 5-Stream虽然PPL更优，但5路CNN+5个手工特征embedding的设计复杂度和调参成本更高。在资源受限或需要快速迭代的场景下，HZK32位图的简洁性是一个实际优势。
